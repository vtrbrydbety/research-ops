## 3. 主要风险

### 风险 A｜数据与磁盘是目前最大的现实风险

你的剩余可写空间是 **367 GB**，但当前无法确认是否足够。

FGI 预处理会先把视频转换成 AVI、提帧、运行 S3FD 人脸检测与裁剪，再把每 30 帧组成一个训练片段，同时生成 48 kHz WAV。代码会产生 `pyavi / pyframes / pywork / pycrop / pytmp` 多套中间数据；README 明确表示只有预处理完成后才可以删除其中四类，并且 `pytmp` 必须保留。

因此：

**367 GB 是否足够：未知。**

不能在未测量单批数据膨胀比例前假设足够。

---

### 风险 B｜论文与固定 Commit 存在一个非常重要的学习率不一致

正式 BMVC 论文写的是：

- Adam
- 100 epochs
- **learning rate = 1e-3**
- weight decay = 1e-5
- batch size = 8。

但固定 Commit 的 `my_train.py` 是：

- batch size = 8
- 100 epochs
- **默认 learning rate = 1e-4**
- weight decay = 1e-5。

而 README 的正式训练命令：

```
python my_train.py --out_dir . --epochs 100 --num_workers 7 --with_att --using_pseudo_fake

```

**没有传** **`--lr`**，所以实际会使用代码默认值 **1e-4**。官方提供的模型路径名称同样包含 `lr0.0001`。

因此：

> **“论文正式实验究竟应以 1e-3 还是公开代码/权重的 1e-4 为准”目前无法从公开材料唯一确定。**

这是后续正式 baseline 必须记录的复现偏差，不能偷偷选一个。

---

### 风险 C｜仓库的数据 CSV 流程存在代码级不一致

README 要求执行：

```
python write_csv.py --out_dir .

```

但固定 Commit 中 `write_csv.py` 对普通测试集生成的是：

```
test_split.csv

```



而 `dataset_3d.py` 在 DFDC test 模式实际读取：

```
test_imbalance_split.csv

```



也就是说，**严格按 README 从头执行，很可能在测试阶段因为 CSV 文件名不一致而需要人工修正/复制/重命名。**

这不是你的环境问题，而是固定 Commit 本身的执行路径不完全闭合。

---

### 风险 D｜三张 GPU 能用于训练，但不会自动解决预处理瓶颈

训练代码把模型包装为：

```
model = nn.DataParallel(model)

```

固定 Commit 没有指定 `device_ids`，而 PyTorch 的 `DataParallel` 默认使用所有可见 CUDA devices，因此你的 3×2080 Ti 理论上可以参与训练。

但是预处理脚本是逐个遍历视频，并在 S3FD 中直接创建：

```
S3FD(device='cuda')

```

仓库本身没有实现三 GPU 数据分片式预处理。

因此三块 GPU **有利于训练，但按原仓库运行不会自动把三块 GPU 都用于预处理**。

---

### 风险 E｜三天能否完整训练属于未知

正式论文使用 15,300 个训练视频、100 epoch、batch size 8。

仓库没有给出：

- 训练使用什么 GPU；
- 单 epoch 时间；
- 总训练时间；
- 峰值显存；
- 完整预处理时间。

因此：

**3 天完成“下载 + 预处理 + 100 epoch 训练 + 测试”的概率目前无法可靠判断。**

不能宣称三天够，也不能宣称一定不够。

**这一步不通过，不进入大规模数据下载。**

### 第二步：做 **数据与磁盘 Gate**

先做三件事，而不是直接下载整个 DFDC：

1. 确认 Kaggle DFDC 是否能实际下载；
2. 确认官方 Google Drive checkpoint 能实际取得；
3. 只取极少数作者列表中的 real/fake 视频，跑完整 `pre-process.py`。

然后实际测：

```

```

- 原始视频大小；
- preprocessing 时间；
- `pyavi`；
- `pyframes`；
- `pycrop`；
- `pytmp`；
- 峰值磁盘占用。

这样才能用真实数据估算 **367 GB 是否足够**，而不是猜。

---

### 第三步：先打通 **最小 baseline 闭环**

目标不是先训练 100 epoch，而是先完成：

```
固定 Commit
    ↓
正确环境
    ↓
少量 DFDC 视频
    ↓
pre-process.py
    ↓
CSV
    ↓
官方 checkpoint
    ↓
my_train.py --test
    ↓
my_test.py
    ↓

```

这里需要特别处理已经确认的固定 Commit 问题：

```

```

在不修改数据内容的前提下，应明确记录这个兼容修正，例如复制：

```
cp test_split.csv test_imbalance_split.csv

```

然后跑官方权重推理。

**只有这个闭环跑通，并拿到实际显存、预处理速度、磁盘占用和推理结果之后，才进入 15,300 样本 × 100 epoch 的正式训练。**
